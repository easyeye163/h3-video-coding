用编程和 AI 智能体共建仓库
做出一个短剧可视化看板

从嵩口古镇 20 集文化短剧说起，聊聊"人 + AI"协作的新范式
AI 协作 开源实践 可视化看板

永泰嵩口古镇，一座有千年历史的闽中水乡。2026 年夏天，一个 20 集的 AI 文化宣传短剧在这里诞生——剧本由 AI 撰写，画面由 AI 生成，配音由 AI 合成。但真正让这个项目跑起来的，不是某个单一模型的能力，而是一套"人写规则、AI 干活、Git 管版本"的协作机制。

这篇文章记录了这个项目中一个具体的工程实践：用一段 Python 脚本自动扫描素材目录，生成可视化看板，再通过 GitHub Pages 免费托管上线。以及这套方法如何迁移到其他行业。

问题：素材一多，全乱了

嵩口短剧项目的素材规模不算大，但也足够让人头疼：5 个角色定妆图、10 张场景参考图、5 段成片视频、14 条备选音色，散落在 images/、videos/、audio/ 三个目录下，子目录还分了好几层。

每次有新素材进来，项目主文档里的进度数字要手动改，看板 HTML 里的链接要手动贴，分集状态要手动标。这些活不难，但烦——而且容易漏。更关键的是，多个 AI 智能体在不同时段各自生成素材、各自更新文档，没有一个统一的"素材账本"，谁也说不清当前到底有多少资产。

于是问题变成：能不能写一段代码，自动扫描目录、统计进度、生成看板？

方案：一个脚本搞定一切

核心思路很简单——Python 脚本扫描三个素材目录，按规则分类，按文件名解析进度，最后拼出一份完整的 HTML 看板。

扫描逻辑

脚本维护一份分类配置，每个分类指定目录路径、文件扩展名、显示名称映射：

# 素材分类配置 ASSET_CATEGORIES = { "characters": { "dir": "images/songkou_characters", "title": "角色定妆图（三视图）", "extensions": {".png", ".jpg", ".jpeg"}, "name_map": {"lin_xiaoxi_three_view.png": "林小溪 · 主角"}, }, "videos_drama": { ... }, "audio_voices": { ... }, }

脚本遍历每个配置项对应的目录，收集文件信息，生成 jsDelivr CDN 链接（中文路径自动 URL 编码），然后把结果填入 HTML 模板。

进度解析

短剧视频的文件名遵循 EP1段1_清晨嵩口.mp4 的命名规则，脚本用正则提取集号和段号，自动计算每集完成了几段、整体完成率多少：

import re for vf in video_files: m = re.match(r"EP(\d+)段(\d+)", vf["filename"]) if m: ep_num = int(m.group(1)) seg_num = int(m.group(2)) episodes[ep_num]["segments"].add(seg_num)

4 段全完成标记为"成片完成"，部分完成标记为"2/4 段"，未开始就是"未开始"。不用手动维护状态表，文件名就是数据源。

自动生成的看板

最终产物是一份自包含的 HTML 文件，包含进度总览、分集矩阵、图片网格、视频播放器、音频试听、里程碑和资产缺口清单。所有素材链接指向 jsDelivr CDN，打开即用：

整个脚本不到 300 行 Python，零第三方依赖，标准库跑通。这大概是"够用就好"的工程哲学——不引入框架、不搭服务、不写 CI，一个文件解决一个真实问题。

上线：GitHub Pages 免费托管

看板生成了，但要分享给别人看。直接把 HTML 文件发给别人不够优雅，用 jsDelivr 链接打开发现浏览器把它当纯文本渲染（因为 CDN 返回的 Content-Type 是 text/plain）。

解决方案是 GitHub Pages——仓库已经在 GitHub 上，调用一次 API 就能开启：

curl -X POST "https://api.github.com/repos/easyeye163/h3-video-coding/pages" \ -H "Authorization: token $GITHUB_TOKEN" \ -d '{"source":{"branch":"main","path":"/"}}'

一两分钟后，看板就能通过 https://easyeye163.github.io/h3-video-coding/songkou-dashboard.html 访问了。Content-Type 正确返回 text/html，浏览器正常渲染，视频能播、图片能看、音频能听。每次 push 到 main 分支自动更新，零运维成本。

关键：AI 智能体如何协作维护仓库

这个项目最有趣的地方不在于某个脚本本身，而在于整个仓库是人和多个 AI 智能体共同维护的。整个协作流程是这样的：

角色 负责什么 产出
人 定需求、审质量、拍板决策、提供 API Key 和素材 项目主文档、创意方向
AI 智能体 A 生成角色定妆图、场景参考图 图片文件 → images/ 目录
AI 智能体 B 撰写六段式提示词、调用 RunningHub API 生成视频 视频文件 → videos/ 目录
AI 智能体 C 合成角色音色 音频文件 → audio/ 目录
看板脚本 扫描三个目录，统计进度，生成 HTML songkou-dashboard.html
Git + GitHub Pages 版本管理、自动部署、CDN 分发 在线可访问的看板

每个智能体只做一件事：把自己产出的文件放到约定的目录里，遵守命名规则。看板脚本自动扫描目录就能反映最新状态。不需要任何智能体之间直接通信，也不需要中心调度器——文件系统就是接口，命名约定就是协议。

这种模式的好处是显而易见的：每个智能体完全解耦，增加或替换任何一个都不影响其他环节。人只需要在关键节点做决策（审图、审片、选音色），其余交给 AI 和脚本自动流转。

延伸：这套方法能用在哪

嵩口项目是一个文化宣传短剧，但"AI 智能体产素材 + 脚本自动汇总 + Git 仓库管理 + 免费静态托管"这套组合拳，本质是一种低成本数字资产管理范式，可以平移到很多行业。

电商产品上新
AI 生成产品图 → 批量写详情页文案 → 自动生成商品上新进度看板（图片/文案/价格/库存状态一栏全览）。仓库即商品库，看板即上架进度表。
教育培训课程制作
AI 生成课件配图 → 语音合成课程旁白 → 自动生成课程开发看板（章/节/素材状态/试听播放器）。一个仓库对应一门课，每个智能体负责一个章节。
房产楼盘展示
AI 生成效果图/户型图 → 合成配音讲解 → 自动生成楼盘素材看板（效果图/视频/户型/周边配套一页全展示）。销售直接发链接给客户，手机打开即看。
文博数字化
AI 生成文物复原图 → 合成讲解音频 → 自动生成数字展厅看板（文物图/讲解音频/复原视频/年代时间线）。一个仓库对应一个展览主题。
自媒体内容矩阵
AI 生成短视频/封面图/文案 → 自动生成内容排期看板（发布日期/平台/素材状态/数据回填）。多个智能体并行产出，看板实时反映排期完成度。

这些场景的共同特征是：素材多、更新频繁、需要可视化呈现、预算有限。用传统的 CMS 或项目管理软件太重，用 Excel 手动维护太累，而"一个脚本 + 一个 Git 仓库 + GitHub Pages"刚好卡在中间——够用、免费、可追踪、可协作。
