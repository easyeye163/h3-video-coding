> 嵩口古镇 20 集文化短剧 · 人 + AI 协作的新范式

`AI协作` `短剧生产` `可视化看板` `开源实践`

---

永泰嵩口古镇，一座有千年历史的闽中水乡。2026 年夏天，一个 20 集的 AI 文化宣传短剧在这里诞生——剧本由 AI 撰写，画面由 AI 生成，配音由 AI 合成，进度由脚本自动汇总，看板由 GitHub Pages 免费托管。整个项目没有一个全职团队，而是**一个人加多个 AI 智能体，围绕一个 Git 仓库协作完成**。

这篇文章完整记录了这套实践——从短剧素材的生产流水线，到可视化看板的自动生成，再到"人 + AI"协作维护仓库的方法论，最后延伸到其他行业的迁移可能。

## 项目全貌

嵩口短剧项目的规模不算大，但环节齐全。整体规格如下：

| 维度 | 规格 | 说明 |
|---|---|---|
| 集数 | 20 集 | 每集一个嵩口文化主题（初见嵩口 / 鹤形之谜 / 万安堡探秘...） |
| 分镜 | 每集 4 段 × 15 秒 | 全剧 80 个镜头段，每段一段独立视频 |
| 角色 | 5 人 | 林小溪 / 陈阿公 / 张导演 / 神秘旅人 / 小糯米 |
| 场景 | 10 处 | 德星楼 / 古码头 / 鹳口祖厝 / 鹤形路 / 宁远庄 / 万安堡等 |
| 音色 | 5 个 | 3 个专属定制 + 2 个复用现有 |
| 技术栈 | H3 + RunningHub + Git | MiniMax H3 六段式提示词驱动 RunningHub 工作流 API |

## 生产流水线

短剧的生产不是一步到位的，而是分五步流水线，每一步产出独立文件存入仓库：

```
Step 1 剧本规划 → Step 2 角色定妆 → Step 3 提示词撰写 → Step 4 API 生成视频 → Step 5 看板汇总
```

### 第一步：剧本与分镜规划

20 集剧本全部由 AI 撰写，每集围绕一个嵩口文化地标展开叙事。剧本不是自由发挥，而是遵循一套结构化模板——每集拆成 4 个镜头段，每段指定场景、角色、机位、情绪弧线和声音设计。剧本层完成后，整个项目的"骨架"就定了，后续所有素材都围绕这个骨架生产。

20 集 × 4 段 = 80 个镜头段的提示词，目前全部就绪，存放在项目主文档中。

### 第二步：角色定妆图与场景参考图

AI 短剧的一个核心难题是角色一致性——同一个角色在 80 段视频里的脸、发型、服装必须稳定。解决方案是**先生成每个角色的三视图定妆照**（正面 / 侧面 / 全身），后续每段视频生成都把定妆图作为输入参考，锁定角色外观。

5 个角色的三视图已经全部生成完毕，加上嵩口全景首帧共 6 张，存放在 `images/songkou_characters/` 目录。场景方面，嵩口实地拍摄了 10 处文化地标的参考照片，存放在 `images/嵩口真实场景图/`，作为画面生成的空间参照。

> 定妆图和场景图都存在 Git 仓库里，通过 jsDelivr CDN 可以直接用 URL 引用。这意味着 AI 智能体生成视频时不需要先上传文件，直接把 GitHub 链接填进 API 参数就行——省掉了一个完整的上传步骤。

### 第三步：六段式 Full-Reference 提示词

这是整个项目最核心的技术环节。每段 15 秒视频的提示词不是简单一句话，而是一套结构化的六段式文档，包含：

| 段落 | 内容 | 作用 |
|---|---|---|
| subject_definitions | 角色与场景的锁定描述 | 规定哪些图片负责什么，全片不得漂移 |
| summary | 整段剧情概述 | 一句话定调：什么人在什么地方发生了什么 |
| retention_analysis | 不变量约束 | 人物不变量 / 场景不变量 / 风格不变量 / 绝对禁止项 |
| detailed_description | 逐镜头详细描述 | 机位、运镜、表演、对白、情绪节奏 |
| overall_soundscape | 环境声设计 | 雨声/脚步/环境底噪/对白/呼吸等声音层 |
| non_diegetic_music | 配乐设计 | BGM 进出点、情绪匹配、乐器选择 |

这套六段式结构确保 AI 生成的视频在角色一致性、场景连贯性、情绪节奏和声音设计上都可控。不是"输入一句话等结果"，而是**用工程文档的方式给 AI 下达精确指令**。

### 第四步：curl 命令即制作单

提示词写好后，要提交给 RunningHub 的视频生成工作流。传统的做法是手动在工作流页面上填参数、上传文件、点提交。但这个项目做了不一样的事——**把每一段的完整 API 调用写成了可直接执行的 curl 命令**，存在项目主文档里。

每段 curl 的核心结构长这样：

```bash
curl --location --request POST 'https://www.runninghub.cn/openapi/v2/run/ai-app/2090774740146413570' \
--header "Authorization: Bearer ${RUNNINGHUB_API_KEY}" \
--data-raw '{
  "nodeInfoList": [
    {"nodeId":"132", "fieldName":"value", "fieldValue":"15"},
    {"nodeId":"115", "fieldName":"aspect_ratio", "fieldValue":"16:9 (Widescreen)"},
    {"nodeId":"137", "fieldName":"image",
     "fieldValue":"https://cdn.jsdelivr.net/gh/.../lin_xiaoxi_three_view.png"},
    {"nodeId":"166", "fieldName":"image",
     "fieldValue":"https://cdn.jsdelivr.net/gh/.../%E5%8F%A4%E7%A0%81%E5%A4%B4.png"},
    {"nodeId":"138", "fieldName":"value", "fieldValue":"<六段式提示词全文>"},
    {"nodeId":"165", "fieldName":"audio",
     "fieldValue":"https://cdn.jsdelivr.net/gh/.../songkou_girl_main.flac"}
  ],
  "instanceType":"default", "usePersonalQueue":"false"
}'
```

这里有几个关键设计：

**素材直接用 GitHub raw 链接**。图片和音频不需要先上传到 RunningHub，直接把 jsDelivr CDN 的完整 URL 填入 fieldValue 字段。中文路径自动做 URL 编码。这一步是通过实测验证的——EP2 段2 一次成功，75 币，372 秒生成。

**未使用的节点保留占位值**。工作流有 4 个图片输入和 2 个音频输入，但不是每段都需要全部填满。对于不需要的图片节点填 `example.png`，不需要的音频节点复用 audio1 的链接——不能留空，否则工作流会报 errorCode 805。

**API Key 从环境变量获取**。curl 模板里写的是 `${RUNNINGHUB_API_KEY}`，实际执行时替换为真实 key。这样提示词文档可以公开分享，不泄露密钥。

> 这个设计的妙处在于：任何 AI 智能体拿到这份 curl，替换 API Key 后直接执行就行——不需要理解工作流的结构、不需要手动填参数、不需要上传文件。提示词文档本身就是可执行的制作单。

目前 EP1 的四段 curl 已经全部写好并验证通过，成片存放在 `videos/songkou_drama/` 目录。EP2-EP20 的提示词也已就绪，等逐段执行即可。

## 问题：素材一多，全乱了

短剧生产的每一步都在往仓库里塞文件——定妆图、场景图、提示词、成片视频、音色文件——很快 `images/`、`videos/`、`audio/` 三个目录下堆了几十个文件。多个 AI 智能体在不同时段各自产出素材，没有一个统一的"素材账本"，谁也说不清当前到底有多少资产。

于是问题变成：**能不能写一段代码，自动扫描目录、统计进度、生成看板？**

## 方案：一个脚本搞定一切

核心思路很简单——Python 脚本扫描三个素材目录，按规则分类，按文件名解析进度，最后拼出一份完整的 HTML 看板。

### 扫描逻辑

脚本维护一份分类配置，每个分类指定目录路径、文件扩展名、显示名称映射：

```python
# 素材分类配置
ASSET_CATEGORIES = {
    "characters": {
        "dir": "images/songkou_characters",
        "title": "角色定妆图（三视图）",
        "extensions": {".png", ".jpg", ".jpeg"},
        "name_map": {"lin_xiaoxi_three_view.png": "林小溪 · 主角"},
    },
    "videos_drama": { ... },
    "audio_voices": { ... },
}
```

脚本遍历每个配置项对应的目录，收集文件信息，生成 jsDelivr CDN 链接（中文路径自动 URL 编码），然后把结果填入 HTML 模板。

### 进度解析

短剧视频的文件名遵循 `EP1段1_清晨嵩口.mp4` 的命名规则，脚本用正则提取集号和段号，自动计算每集完成了几段、整体完成率多少：

```python
import re

for vf in video_files:
    m = re.match(r"EP(\d+)段(\d+)", vf["filename"])
    if m:
        ep_num = int(m.group(1))
        seg_num = int(m.group(2))
        episodes[ep_num]["segments"].add(seg_num)
```

4 段全完成标记为"成片完成"，部分完成标记为"2/4 段"，未开始就是"未开始"。不用手动维护状态表，文件名就是数据源。

### 自动生成的看板

最终产物是一份自包含的 HTML 文件，包含进度总览、分集矩阵、图片网格、视频播放器、音频试听、里程碑和资产缺口清单。所有素材链接指向 jsDelivr CDN，打开即用：

> 看板效果示意：包含进度总览（剧集完成 1/20、镜头段 4/80、定妆图 6/5）、分集矩阵、素材缩略图网格。实际看板包含全部 43 个素材链接。

脚本还支持 `--watch` 监控模式，每 3 秒检测一次文件变化，有新素材进来就自动刷新看板。整个脚本不到 300 行 Python，零第三方依赖，标准库跑通。

## 上线：GitHub Pages 免费托管

看板生成了，但要分享给别人看。直接把 HTML 文件发给别人不够优雅，用 jsDelivr 链接打开发现浏览器把它当纯文本渲染（因为 CDN 返回的 Content-Type 是 text/plain）。

解决方案是 GitHub Pages——仓库已经在 GitHub 上，调用一次 API 就能开启：

```bash
curl -X POST "https://api.github.com/repos/easyeye163/h3-video-coding/pages" \
  -H "Authorization: token $GITHUB_TOKEN" \
  -d '{"source":{"branch":"main","path":"/"}}'
```

一两分钟后，看板就能通过 `https://easyeye163.github.io/h3-video-coding/songkou-dashboard.html` 访问了。Content-Type 正确返回 `text/html`，浏览器正常渲染，视频能播、图片能看、音频能听。每次 push 到 main 分支自动更新，零运维成本。

## 核心：AI 智能体如何协作维护仓库

这个项目最有趣的地方不在于某个脚本或某段提示词，而在于**整个仓库是人和多个 AI 智能体共同维护**的。整个协作流程是这样的：

| 角色 | 负责什么 | 产出 |
|---|---|---|
| 人 | 定需求、审质量、拍板决策、提供 API Key | 项目主文档、创意方向 |
| AI 智能体 A | 生成角色定妆图、场景参考图 | 图片文件 → images/ 目录 |
| AI 智能体 B | 撰写六段式提示词、执行 curl 调 RunningHub API 生成视频 | 视频文件 → videos/ 目录 |
| AI 智能体 C | 合成角色音色 | 音频文件 → audio/ 目录 |
| 看板脚本 | 扫描三个目录，统计进度，生成 HTML | songkou-dashboard.html |
| Git + GitHub Pages | 版本管理、自动部署、CDN 分发 | 在线可访问的看板 |

每个智能体只做一件事：把自己产出的文件放到约定的目录里，遵守命名规则。看板脚本自动扫描目录就能反映最新状态。不需要任何智能体之间直接通信，也不需要中心调度器——**文件系统就是接口，命名约定就是协议**。

更关键的是，提示词被写成了可直接执行的 curl 命令，存放在 Markdown 文档里。任何 AI 智能体打开文档，替换 API Key，直接执行就能生成视频。**文档即程序，提示词即制作单**——不需要额外的任务编排系统。

> 这种模式的好处是显而易见的：每个智能体完全解耦，增加或替换任何一个都不影响其他环节。人只需要在关键节点做决策（审图、审片、选音色），其余交给 AI 和脚本自动流转。

## 延伸：这套方法能用在哪

嵩口项目是一个文化宣传短剧，但"AI 智能体产素材 + curl 命令即制作单 + 脚本自动汇总 + Git 仓库管理 + 免费静态托管"这套组合拳，本质是一种**低成本数字资产管理范式**，可以平移到很多行业。

### 电商产品上新

AI 生成产品图 → 批量写详情页文案 → curl 调用生成产品展示视频 → 自动生成商品上新进度看板（图片/文案/价格/视频状态一栏全览）。仓库即商品库，看板即上架进度表。

### 教育培训课程制作

AI 生成课件配图 → 语音合成课程旁白 → curl 生成教学动画视频 → 自动生成课程开发看板（章/节/素材状态/试听播放器）。一个仓库对应一门课，每个智能体负责一个章节。

### 房产楼盘展示

AI 生成效果图/户型图 → 合成配音讲解 → curl 生成楼盘漫游视频 → 自动生成楼盘素材看板（效果图/视频/户型/周边配套一页全展示）。销售直接发链接给客户，手机打开即看。

### 文博数字化

AI 生成文物复原图 → 合成讲解音频 → curl 生成复原过程视频 → 自动生成数字展厅看板（文物图/讲解音频/复原视频/年代时间线）。一个仓库对应一个展览主题。

### 自媒体内容矩阵

AI 生成短视频/封面图/文案 → curl 批量生成 → 自动生成内容排期看板（发布日期/平台/素材状态/数据回填）。多个智能体并行产出，看板实时反映排期完成度。

这些场景的共同特征是：**素材多、更新频繁、需要可视化呈现、预算有限**。用传统的 CMS 或项目管理软件太重，用 Excel 手动维护太累，而"一个脚本 + 一个 Git 仓库 + GitHub Pages"刚好卡在中间——够用、免费、可追踪、可协作。
